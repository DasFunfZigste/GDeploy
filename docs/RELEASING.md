# Publishing an iteration of GDeploy

User-facing releases live at https://github.com/DasFunfZigste/GDeploy/releases. Each new release starts with the short Ubuntu 24.04 installation/update guide, followed by its version-specific changelog, versioned image and immutable digest, optional deploy bundle, Docker image archive and SHA-256 checksums. Keep historical published release notes, assets and tags unchanged.

## Prepare a version

1. Choose a new semantic version (`X.Y.Z`). Patch versions fix compatible behavior, minor versions add compatible features, and major versions change compatibility. The initial 0.x series remains for lab validation.
2. Update `version` in `pyproject.toml` and `__version__` in `gdeploy/__init__.py`. The API reads the latter. Also update the default image version in `compose.release.yaml` and `Dockerfile`, current version/image examples in `README.md`, `docs/INSTALL.md` and `docs/OPERATIONS.md`, and the installation guide's version-pinned operations link. Preserve historical compatibility notes.
3. Add a dated `## [X.Y.Z] - YYYY-MM-DD` section in `CHANGELOG.md`, describing user-visible changes, installation/upgrade implications and remaining limitations. Move completed items out of Unreleased.
4. Run `pytest -q`, `ruff check .`, and `python scripts/build_release.py --tag vX.Y.Z --validate-only`. Review installation examples and any database compatibility changes.
5. Commit and push the reviewed changes, then tag that exact commit:

   ```sh
   git tag -a vX.Y.Z -m "GDeploy vX.Y.Z"
   git push origin vX.Y.Z
   ```

The tag workflow tests the code, builds the image, verifies automatic and manual bootstrap, required replacement of default credentials, Compose/Docker CLI login, account persistence, and OS ISO upload/selection persistence, publishes to GHCR, verifies a pull by digest and a Docker archive load, then builds and uploads release assets. It publishes the GitHub Release only after all those checks pass. A normal branch commit does not create a release; the tag defines a finished iteration.

## Distribution and permissions

The repository and release downloads are public. GHCR package visibility is a separate setting; do not claim it is public without verifying that independently. The default user path is the public source clone and local Compose build, requiring no GitHub account linking or registry login. The optional release image archive can be downloaded from GitHub and loaded with `docker load`, then started with `--pull never`.

The publishing workflow still authenticates to GHCR using GitHub's short-lived `GITHUB_TOKEN` with `contents: write` and `packages: write`; no personal publishing token is stored. OCI metadata links the package to this repository. Keep that publishing authentication in place even though users of the default source installation do not need a registry login.

Keep `docs/INSTALL.md` concise: Ubuntu 24.04 package installation, clone/build/start, first sign-in and Setup, then updating from the same clone. Use `sudo apt install -y git docker.io docker-compose-v2 docker-buildx` and `sudo docker compose up -d --build --wait`; existing Docker/Git installations skip package setup. Explain that cloning and `git pull --ff-only` track the current default branch rather than a version pinned by an archived release page. Do not add GitHub CLI authentication, personal tokens, registry login or the advanced release-bundle route to the primary walkthrough. Link detailed operations instead.

The image currently targets `linux/amd64`. Versioned image tags are convenient references; the release also records the immutable registry digest. No moving `latest` image tag is published, so deployment examples always select an explicit version. The latest-release page is available at https://github.com/DasFunfZigste/GDeploy/releases/latest.

The release Compose file requires Docker Compose 2.24 or later so `.env` can be optional. A fresh data volume starts with `admin`/`admin` and a unique random encryption key; the manual configuration script uses the same initial login. Verify that business APIs remain blocked until the required account change, the completed change invalidates existing sessions, and the default login then fails. Existing random/custom credentials must remain valid on upgrade, and a saved database account must survive restart without being overwritten by bootstrap settings. Check both configuration paths and ensure a missing key for existing data cannot cause silent key replacement. Include the short `docs/INSTALL.md` directly at the start of each new release page and retain detailed startup recovery in `docs/OPERATIONS.md`.

For ESXi certificate trust, validate that API and datastore download/upload connections enforce the approved certificate for the exact endpoint, reject changed/expired/not-yet-valid certificates, and retain approvals after restart. Check trust removal and the ordinary CA verification path. Record actual ESXi acceptance separately from local TLS transport tests.

For ESXi datastore media, verify authentication/CSRF/account setup gates, safe datastore and folder selection, rejection of stale host selections, streamed download limits, publisher-checksum validation, low-disk and interrupted-copy cleanup, and persistence of verified copies with their origin details. Failed browsing or imports must preserve the previously saved media. Keep browser upload and mounted-media regression coverage. The datastore source must only read the original file; deployment remastering uses the retained local copy and cleanup must never delete the original. Use [the lab checklist](LAB_VALIDATION.md) to record real browse/download permissions, TLS failures and unattended installation against a standalone ESXi host. Do not present mocked transport tests as live ESXi acceptance.

For deployment diagnostics and storage management, verify expandable/copyable logs and secret redaction, including tools that fail while preparing media. Check that historical generic errors remain identified as previously recorded information. Exercise real xorriso preparation as the non-root image user with read-only extracted metadata, a source checksum unchanged after preparation, temporary files under the private `/data/artifacts` workspace, and output exceeding the separate 256 MiB `/tmp` limit. Record this container regression separately from a real Ubuntu/ESXi boot.

Verify container-visible data-filesystem usage against its actual mount. Deletion tests must cover uploaded and ESXi-imported copies, current-selection and queued/running/cleaning reference protection, stale browser requests, concurrent selection/deployment changes, rejected unsafe paths or symlinks, and retained original ESXi/server files. Check **Clear saved selection** with and without environment-configured fallback, including clearing and then deleting the sole unused copy without a replacement upload. Clearing must preserve the file and active-job snapshots/protection. Confirm clearing/deletion require administrator authentication, completed account setup and CSRF protection, and deletion has an explicit UI confirmation with audit history retained. Do not describe data reporting as whole-host access, or claim the release expands Docker/host storage.

For history visibility, verify hiding/restoring through both history and details, **Show hidden**, direct links, search/status filtering and persistence after a restart. Authentication, account setup and CSRF checks must apply. Queued/running/cleaning jobs must reject hiding even from stale requests. Confirm records retain status, logs, credentials, VM ownership and resource reservations, and no ESXi operation is invoked. Hiding must not make a failed job appear successful or advertise readiness/cleanup that did not occur.

For per-VM configuration, select Elasticsearch and Kibana together and exercise all five roles, including FleetManager. Verify independently entered names, resources, datastore, port group and DHCP/static settings survive wizard navigation and reach the existing per-VM API specification. Check duplicate-name/resource validation, preflight invalidation, role dependencies, and desktop/mobile/keyboard usability. **Setup** must precede **Deployments** in navigation. Use the lab checklist to verify actual VM configuration on ESXi separately from browser/API tests.

The release bundle uses an explicit file allowlist, including `docs/FLEETMANAGER.md` and `docs/OPERATIONS.md`. It is an optional prebuilt-image deployment bundle, not a source checkout; do not add application source merely to support the default clone instructions. It must never contain `.env`, `docker.env`, `bootstrap.json`, bootstrap credentials, data volumes, private certificates/product identity PEMs, Ubuntu ISOs or licensed software/dependency installers. Checksums cover each downloadable payload; download them through the project's official HTTPS release page to check for corrupted or mismatched files.

For administrator SSH access, test single/multiple/duplicate public keys, rejected private or malformed keys, authenticated and CSRF-protected saving, persistence, and non-destructive clearing. Verify each queued job captures its own list, all VM roles receive that snapshot alongside their unique automation key, older jobs without a snapshot remain supported, and replacement jobs use current settings. Inspect the generated NoCloud YAML and real remastered ISO; validate actual guest SSH authentication separately with the lab checklist. Exercise all Setup tabs on desktop/mobile and ensure draft errors and comments render safely.

For Splunk packages, verify authenticated and CSRF-protected upload, server selection, clearing and deletion. Cover vendor `.tgz` filenames, publisher SHA-512 and SHA-256 verification through both sources, rejection of incorrect hashes or invalid lengths, expected Linux x86_64 Splunk archive validation, the 4 GiB upload limit, interrupted/low-space cleanup and persistence. Check that the instructions point to Splunk's official `.sha512` download and existing saved SHA-256 selections work without re-upload. Reject unsafe archives or filesystem links, preserve the previous choice on failed validation and keep mounted source files outside deletion controls. Selected packages and queued/running/cleaning snapshots must remain protected under stale and concurrent requests.

Verify new queued jobs retain their original package path and computed SHA-256 after changing or clearing Setup, including packages saved with a publisher SHA-512. Confirm guest transfer verification still checks that queued SHA-256 before package-manager or extraction work, pre-v0.8.0 jobs keep environment package behavior, and new replacement jobs use current selections. Test the missing-package preflight link, retained per-VM draft, return to the prior wizard step and fresh preflight before deployment. OS ISO checksums, release asset checksums and `GDEPLOY_SPLUNK_SHA256` remain SHA-256. Record actual licensed-package guest installation separately from synthetic archive and browser tests. Keep release asset formats and the existing allowlist unchanged; never add a user's Splunk installer or license to the image/bundle.

For FleetManager, verify both Setup modes, redacted response fields, encrypted settings/license storage, blank-field retention, first-certificate/private-key matching and valid dates. Test native Debian metadata on Linux with `dpkg-deb`; metadata mocks alone are insufficient. Cover streamed 4 GiB uploads, optional expected SHA-256, interrupted/low-space cleanup, server browsing, main/dependency selection, active-reference protection and atomic deletion/queue insertion. Check source/checksum validation again in the guest before package-manager work and preserve existing roles. Online mode must ignore old offline package selections, use verified TLS for the signing key, reject key-endpoint redirects, and retain appropriately protected apt credentials/configuration. Offline mode must use the regular live-server source and local packages with no repository-download fallback; test missing dependencies explicitly.

Verify the FleetManager guest resource checks, ownership and permissions of its product identity PEM, `corelight-fleetd` health, exact-certificate HTTPS check, sensor listener and temporary administrator result. Ordinary diagnostics must redact community strings, tokens, license material and generated passwords. The authenticated Credentials view may reveal the snapshotted community string and initial application password. Test required first-sign-in password guidance, software navigation, per-VM resource forms and return from Setup to the deployment draft on desktop/mobile. Use [the FleetManager lab checks](LAB_VALIDATION.md#fleetmanager-installation) for actual licensed-package/ESXi/sensor acceptance, and state clearly when that testing has not been performed.

For the FleetManager wizard flow introduced in v0.9.1, verify **Choose software → Configure VMs → FleetManager configuration → Review & deploy** appears whenever the role is selected, including with saved defaults. Both installation modes, secrets/license retention, package selection/uploads and validation must work before any preflight. **Save & continue** saves through the existing settings API and updates defaults before advancing; it must not run preflight or create a deployment. Review retains the explicit **Run preflight** action. Check invalid configuration, concurrent uploads/saves, backward navigation, returning from Setup, role removal/reselection and fresh-preflight requirements after changes. Non-Fleet deployments must retain the three-step wizard. Exercise keyboard/mobile layout and preserve the existing API and guest-installation regression checks.

For FleetManager online version selection, test blank/latest, an exact Debian version including revisions/epochs, invalid values, explicit clearing and legacy settings/jobs without the field. Verify Setup and wizard defaults, review/preflight messages, dirty-state invalidation and immutable queued snapshots. Preflight validates configuration, not remote availability; the guest must install the exact requested version without substitution and detect unavailable or mismatched versions. Preserve offline package behavior and ordinary future upgrades without apt holds. Confirm a rollback to a release that ignores the selection is documented, and record real licensed-repository acceptance separately from synthetic tests.

## Failed publication

Before publication, the workflow may leave an image tag or draft release. Inspect the failed run and rerun only if the same tagged source is still correct; changing code requires a new version/tag. Published release versions are never overwritten by the workflow. If a draft is retained, a successful rerun refreshes its assets and notes before publishing. A release does not assert that live ESXi acceptance has passed unless that testing has actually been completed and recorded.

Existing installations preserve any `.env`/`docker.env` and their chosen data volume through upgrades. Automatic installations keep their encryption key and initial administrator hash in `/data/bootstrap.json`; their backup must include that file alongside the database containing the chosen administrator account. Bootstrap credential files record only the initial login and are not updated after account setup. Never regenerate the encryption key for an existing database or recommend deleting a volume to fix startup. Restore missing or damaged credentials from the matching backup. Document backup or migration requirements in each release's changelog before publication. The administrator-account migration introduced in version **0.1.3** keeps existing credentials, but older application versions ignore that database account and use the old bootstrap/environment login; rollback notes must address that difference explicitly.

Media backups must include uploaded and ESXi-imported copies under `/data/media`, plus separately mounted server media. Versions before **0.4.0** cannot use the `source="esxi"` media records introduced by datastore import. Before rollback, finish or resolve active jobs and select a verified uploaded or server-mounted ISO that the target version supports; keep the original data volume and encryption keys.

Version **0.5.0** adds explicit deletion of eligible saved ISO copies. Rolling back an image cannot restore files an administrator deleted; use a matching backup or upload/import the source again. The release keeps the existing data volume and adds no app storage quota. Capacity changes belong to the Docker host's backing storage administration and must preserve the complete volume and credentials.

Version **0.6.0** adds the history-visibility `hidden_at` column without replacing deployment records or changing their provisioning status. Older releases use positional inserts that fail with this expanded deployment schema. Require a complete pre-upgrade data-volume backup and restore the matching backup with its encryption configuration for rollback; changing only the image tag is insufficient. Inspect ESXi state before resuming work because the database backup does not undo later VM changes. The per-VM API format and cloud-init readiness check are unchanged.

The certificate-trust table introduced in version **0.2.0** is additive and belongs in the complete data-volume backup. Older versions ignore these approvals and use their previous TLS settings, including any saved `verify_tls=false`. Release and rollback notes must require reviewing those settings and ensuring certificate verification is enabled. A host trusted only through an app approval will need a CA trust configuration for verification in the older release.

Version **0.7.0** adds an encrypted SSH public-key settings record and a key snapshot in new deployments. Earlier versions ignore those administrator keys, including queued snapshots; finish queued work before rollback. Changing app versions or clearing the default list does not change keys already installed on existing guests. Preserve the data volume and encryption key; the earlier schema compatibility caveats still apply when rolling back before v0.6.0.

Version **0.8.0** adds saved Splunk package settings and immutable path/checksum snapshots in newly queued deployments. Include uploaded packages under `/data/packages` in complete data-volume backups and keep separate backups of mounted packages. Earlier releases ignore these selections/snapshots and use environment configuration, so finish queued work before rollback and supply the older version's verified package path/checksum. Deletion permanently removes an eligible uploaded copy; reverting the image cannot restore it or change already installed guest software. Retain the original data volume, encryption configuration and backup; earlier schema compatibility caveats still apply.

Version **0.8.1** adds publisher SHA-512 input while retaining the internal SHA-256 used by package settings and queued snapshots. Existing saved SHA-256 choices need no re-upload or migration. Preserve the published v0.8.0 tag and release history; this checksum-input correction is a new patch release.

Version **0.9.0** adds encrypted FleetManager settings/package records, offline package files and a new VM role. Back up the entire volume, including `/data/fleetmanager-packages`, with the original encryption key; back up mounted packages, vendor license records and guest data separately. Older GDeploy releases do not support FleetManager jobs, so finish or resolve them before rollback and retain the backup. Changing GDeploy versions does not upgrade software on existing guests or reverse deleted files. Never include customer credentials, licenses or installers in the published release; the new walkthrough belongs in the explicit documentation allowlist.

Version **0.9.1** changes the wizard flow and documentation using the existing FleetManager settings API. It introduces no backend/data migration or guest-installation change; retain saved defaults, licenses, packages and queued snapshots. The v0.9.0 backup and role-compatibility requirements continue to apply.

Version **0.9.2** simplifies the default installation and new release-page presentation for public repository access. It moves the longer operational reference into `docs/OPERATIONS.md` without changing the application or stored data. Preserve existing volumes, environment files, keys, media and credentials when rebuilding from the same clone. Repository visibility and GHCR package visibility remain separate; test anonymous source/release downloads before claiming public access.

Version **0.10.0** adds an optional FleetManager online version in encrypted settings and job snapshots, with no database migration. Existing absent/blank choices retain latest-candidate behavior. Finish version-specific jobs before rollback to a release that ignores the selection. Preserve the full data volume and original encryption configuration; changing GDeploy does not upgrade or downgrade existing guests.
