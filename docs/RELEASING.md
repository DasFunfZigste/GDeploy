# Publishing an iteration of GDeploy

User-facing releases live at https://github.com/DasFunfZigste/GDeploy/releases. Each release includes a version-specific changelog, complete Ubuntu/Docker installation walkthrough, versioned image and immutable digest, deploy bundle, Docker image archive and SHA-256 checksums.

## Prepare a version

1. Choose a new semantic version (`X.Y.Z`). Patch versions fix compatible behavior, minor versions add compatible features, and major versions change compatibility. The initial 0.x series remains for lab validation.
2. Update `version` in `pyproject.toml` and `__version__` in `gdeploy/__init__.py`. The API reads the latter. Also update the default image version in `compose.release.yaml` and `Dockerfile`, and image/version examples in `README.md` and `docs/INSTALL.md`.
3. Add a dated `## [X.Y.Z] - YYYY-MM-DD` section in `CHANGELOG.md`, describing user-visible changes, installation/upgrade implications and remaining limitations. Move completed items out of Unreleased.
4. Run `pytest -q`, `ruff check .`, and `python scripts/build_release.py --tag vX.Y.Z --validate-only`. Review installation examples and any database compatibility changes.
5. Commit and push the reviewed changes, then tag that exact commit:

   ```sh
   git tag -a vX.Y.Z -m "GDeploy vX.Y.Z"
   git push origin vX.Y.Z
   ```

The tag workflow tests the code, builds the image, verifies automatic and manual bootstrap, required replacement of default credentials, Compose/Docker CLI login, account persistence, and OS ISO upload/selection persistence, publishes to GHCR, verifies a pull by digest and a Docker archive load, then builds and uploads release assets. It publishes the GitHub Release only after all those checks pass. A normal branch commit does not create a release; the tag defines a finished iteration.

## Distribution and permissions

The repository and GHCR package remain private. The workflow uses GitHub's short-lived `GITHUB_TOKEN` with `contents: write` and `packages: write`; no personal publishing token is stored. OCI metadata links the package to this repository. Users can pull with a classic PAT with `read:packages`, or download the private release's image archive using their repository access and load it locally.

The image currently targets `linux/amd64`. Versioned image tags are convenient references; the release also records the immutable registry digest. No moving `latest` image tag is published, so deployment examples always select an explicit version. The latest-release page is available at https://github.com/DasFunfZigste/GDeploy/releases/latest.

The release Compose file requires Docker Compose 2.24 or later so `.env` can be optional. A fresh data volume starts with `admin`/`admin` and a unique random encryption key; the manual configuration script uses the same initial login. Verify that business APIs remain blocked until the required account change, the completed change invalidates existing sessions, and the default login then fails. Existing random/custom credentials must remain valid on upgrade, and a saved database account must survive restart without being overwritten by bootstrap settings. Check both configuration paths and ensure a missing key for existing data cannot cause silent key replacement. The source quick start and startup recovery instructions in `docs/INSTALL.md` are included directly on each release page.

For ESXi certificate trust, validate that API and datastore download/upload connections enforce the approved certificate for the exact endpoint, reject changed/expired/not-yet-valid certificates, and retain approvals after restart. Check trust removal and the ordinary CA verification path. Record actual ESXi acceptance separately from local TLS transport tests.

For ESXi datastore media, verify authentication/CSRF/account setup gates, safe datastore and folder selection, rejection of stale host selections, streamed download limits, publisher-checksum validation, low-disk and interrupted-copy cleanup, and persistence of verified copies with their origin details. Failed browsing or imports must preserve the previously saved media. Keep browser upload and mounted-media regression coverage. The datastore source must only read the original file; deployment remastering uses the retained local copy and cleanup must never delete the original. Use [the lab checklist](LAB_VALIDATION.md) to record real browse/download permissions, TLS failures and unattended installation against a standalone ESXi host. Do not present mocked transport tests as live ESXi acceptance.

For deployment diagnostics and storage management, verify expandable/copyable logs and secret redaction, including tools that fail while preparing media. Check that historical generic errors remain identified as previously recorded information. Exercise real xorriso preparation as the non-root image user with read-only extracted metadata, a source checksum unchanged after preparation, temporary files under the private `/data/artifacts` workspace, and output exceeding the separate 256 MiB `/tmp` limit. Record this container regression separately from a real Ubuntu/ESXi boot.

Verify container-visible data-filesystem usage against its actual mount. Deletion tests must cover uploaded and ESXi-imported copies, current-selection and queued/running/cleaning reference protection, stale browser requests, concurrent selection/deployment changes, rejected unsafe paths or symlinks, and retained original ESXi/server files. Check **Clear saved selection** with and without environment-configured fallback, including clearing and then deleting the sole unused copy without a replacement upload. Clearing must preserve the file and active-job snapshots/protection. Confirm clearing/deletion require administrator authentication, completed account setup and CSRF protection, and deletion has an explicit UI confirmation with audit history retained. Do not describe data reporting as whole-host access, or claim the release expands Docker/host storage.

For history visibility, verify hiding/restoring through both history and details, **Show hidden**, direct links, search/status filtering and persistence after a restart. Authentication, account setup and CSRF checks must apply. Queued/running/cleaning jobs must reject hiding even from stale requests. Confirm records retain status, logs, credentials, VM ownership and resource reservations, and no ESXi operation is invoked. Hiding must not make a failed job appear successful or advertise readiness/cleanup that did not occur.

For per-VM configuration, select Elasticsearch and Kibana together and exercise all four roles. Verify independently entered names, resources, datastore, port group and DHCP/static settings survive wizard navigation and reach the existing per-VM API specification. Check duplicate-name/resource validation, preflight invalidation, role dependencies, and desktop/mobile/keyboard usability. **Setup** must precede **Deployments** in navigation. Use the lab checklist to verify actual VM configuration on ESXi separately from browser/API tests.

The release bundle uses an explicit file allowlist. It must never contain `.env`, `docker.env`, `bootstrap.json`, bootstrap credentials, data volumes, private certificates, Ubuntu ISOs or Splunk installers. Checksums cover each downloadable payload; GitHub's authenticated release transport supplies the download source, while the checksums detect corrupted or mismatched files.

For administrator SSH access, test single/multiple/duplicate public keys, rejected private or malformed keys, authenticated and CSRF-protected saving, persistence, and non-destructive clearing. Verify each queued job captures its own list, all VM roles receive that snapshot alongside their unique automation key, older jobs without a snapshot remain supported, and replacement jobs use current settings. Inspect the generated NoCloud YAML and real remastered ISO; validate actual guest SSH authentication separately with the lab checklist. Exercise all three Setup tabs on desktop/mobile and ensure draft errors and comments render safely.

## Failed publication

Before publication, the workflow may leave a private image tag or draft release. Inspect the failed run and rerun only if the same tagged source is still correct; changing code requires a new version/tag. Published release versions are never overwritten by the workflow. If a draft is retained, a successful rerun refreshes its assets and notes before publishing. A release does not assert that live ESXi acceptance has passed unless that testing has actually been completed and recorded.

Existing installations preserve any `.env`/`docker.env` and their chosen data volume through upgrades. Automatic installations keep their encryption key and initial administrator hash in `/data/bootstrap.json`; their backup must include that file alongside the database containing the chosen administrator account. Bootstrap credential files record only the initial login and are not updated after account setup. Never regenerate the encryption key for an existing database or recommend deleting a volume to fix startup. Restore missing or damaged credentials from the matching backup. Document backup or migration requirements in each release's changelog before publication. The administrator-account migration introduced in version **0.1.3** keeps existing credentials, but older application versions ignore that database account and use the old bootstrap/environment login; rollback notes must address that difference explicitly.

Media backups must include uploaded and ESXi-imported copies under `/data/media`, plus separately mounted server media. Versions before **0.4.0** cannot use the `source="esxi"` media records introduced by datastore import. Before rollback, finish or resolve active jobs and select a verified uploaded or server-mounted ISO that the target version supports; keep the original data volume and encryption keys.

Version **0.5.0** adds explicit deletion of eligible saved ISO copies. Rolling back an image cannot restore files an administrator deleted; use a matching backup or upload/import the source again. The release keeps the existing data volume and adds no app storage quota. Capacity changes belong to the Docker host's backing storage administration and must preserve the complete volume and credentials.

Version **0.6.0** adds the history-visibility `hidden_at` column without replacing deployment records or changing their provisioning status. Older releases use positional inserts that fail with this expanded deployment schema. Require a complete pre-upgrade data-volume backup and restore the matching backup with its encryption configuration for rollback; changing only the image tag is insufficient. Inspect ESXi state before resuming work because the database backup does not undo later VM changes. The per-VM API format and cloud-init readiness check are unchanged.

The certificate-trust table introduced in version **0.2.0** is additive and belongs in the complete data-volume backup. Older versions ignore these approvals and use their previous TLS settings, including any saved `verify_tls=false`. Release and rollback notes must require reviewing those settings and ensuring certificate verification is enabled. A host trusted only through an app approval will need a CA trust configuration for verification in the older release.

Version **0.7.0** adds an encrypted SSH public-key settings record and a key snapshot in new deployments. Earlier versions ignore those administrator keys, including queued snapshots; finish queued work before rollback. Changing app versions or clearing the default list does not change keys already installed on existing guests. Preserve the data volume and encryption key; the earlier schema compatibility caveats still apply when rolling back before v0.6.0.
